## 1. 场景背景与痛点

### 1.1 场景

北京邮电大学西土城路校区，教学区、学生公寓、食堂、科研楼、服务点分散。日常存在大量小件配送：

- 实验材料、文件、会议资料；
- 饮用水、餐食、快递；
- 临时活动物资。

### 1.2 现有方式的痛点

| 痛点 | 具体表现 |
| --- | --- |
| 多站点顺序靠经验 | 先送哪站、哪站优先，靠人记；截止时间容易冲突 |
| 道路变化无法快速响应 | 施工、活动封路后，原路线失效，需要重新排剩余站点 |
| 信息分散 | 需求在微信/口头，路线在纸上，异常靠电话 |
| 模拟与真实混在一起 | 演示数据和真实配送记录无法区分，验收困难 |
| 责任与过程不可追溯 | 谁接的单、谁改的状态、哪个 Agent 做了什么，没有记录 |

### 1.3 目标

把一句自然语言需求，变成：

```text
结构化任务 → 可执行计划 → 执行状态 → 异常处理 → 可追溯报告
```

**边界：** 系统不控制真实车辆，不做自动驾驶；虚拟车辆与局部绕行只用于演示。

## 2. 方案总览

### 2.1 一句话

> CampusPilot 不替配送员开车，它替配送员**想清楚怎么送、封路后怎么改**。

### 2.2 业务闭环

```text
① 描述需求（自然语言）
        ↓
② 解析 + 逐项补问
        ↓
③ 生成计划（顺序、路线、ETA）
        ↓
④ 执行（开始 / 取货 / 到达 / 交付）
        ↓
⑤ 异常上报（人工 / 上游语义）
        ↓
⑥ 停车 → 判断 → 等待 / 局部绕行 / 重规划
        ↓
⑦ 完成 → 报告 → 历史任务
        ↓
⑧ 管理员接单 / 状态 / 备注
```

### 2.3 三类用户

| 角色 | 主要操作 |
| --- | --- |
| 任务发起人 | 描述需求、补全信息、确认创建 |
| 配送员 | 查看清单、开始/到达/取货/交付、上报异常 |
| 管理员 | 接单、更新任务状态、写处理备注、查看报告 |

## 3. 功能架构

```text
┌──────────────────────────────────────────────┐
│ 交互层（React + TypeScript）                  │
│ 工作台 / 校园地图 / 执行控制 / 管理员 / 报告   │
└──────────────────────┬───────────────────────┘
                       │ REST /api
┌──────────────────────▼───────────────────────┐
│ API 层（FastAPI，单端口 8000）                 │
│ 页面 + 静态资源 + 业务接口同源托管             │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│ Agent 层（三个分工角色 + 调用痕迹）            │
│ 任务规划 Agent / 道路观察 Agent / 调度复盘 Agent│
└──────────────────────┬───────────────────────┘
                       │ 工具调用
┌──────────────────────▼───────────────────────┐
│ 确定性引擎                                     │
│ 白名单校验 / Dijkstra / 站点排序 / 状态机      │
│ 模拟推进 / 重规划 / 报告指标                   │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│ 数据层                                         │
│ SQLite（任务/站点/计划/事件/Agent 痕迹/接单/备注）│
│ 地图 JSON + 校园底图                            │
└──────────────────────────────────────────────┘
```

### 3.1 设计原则

- **Agent 只负责理解、判断和编排**；
- 日期、任务状态、地点白名单、优先级排序、路径与报告指标由**确定性代码**计算；
- 模型不能直接执行任意命令，也不能在用户确认前把任务标记为完成；
- 模拟任务与真实任务隔离，模拟结果不计入真实配送成果。

## 4. 已实现功能

### 4.1 任务创建与逐项补问

- 自然语言输入，示例句式一键填入；
- 解析结果可编辑：取货点、站点、物品、优先级、截止时间；
- 缺失信息用**带编号的问题卡片**逐项追问：
  - 缺取货点 → 卡片内下拉选择；
  - 缺站点 → 一键添加；
  - 缺物品 → 统一物品一键应用到所有站点；
  - 白名单外地名 → 明确提示，不静默丢弃；
- 关键项未补全时，“确认任务信息”按钮禁用。

### 4.2 任务解析（规则 + DeepSeek）

- 规则解析：地点别名、数量、物品、优先级、中文时间（“下午4点半” → 16:30）；
- 真实模型：DeepSeek `deepseek-chat`，OpenAI 兼容接口；
- 模型失败或无有效取货点时**自动回落规则解析**，并明确标注；
- 地点白名单校验，模型不能创建新地点；
- 20 条人工标注样例集：规则 **20/20**，DeepSeek **20/20**（18 条模型 + 2 条规则兜底）。

### 4.3 校园地图与路网

- 底图：团队标注的《北京邮电大学西土城路校区示意图》，2491×3509；
- 可交互地点：**80 个**（41 栋建筑 + 39 个服务点），另有 6 个校门；
- 分类：教学与科研、学生公寓、生活服务、场馆与后勤；
- 路网：6 纵 × 10 横道路网格，**217 个节点、261 段道路**；
- 每个地点用短入口线接入最近路口，路线只走道路网格；
- 距离按约 0.28 米/像素估算，页面明确标注“示例估算”；
- 服务点在地图上显示为小蓝点，悬停显示名称，避免 80 个标签重叠。

### 4.4 计划与执行

- 多站点排序：优先站点前置、截止时间约束；
- 路线：Dijkstra，支持单行道与封路；
- 输出：站点顺序、物品、ETA、路线、预计耗时、不可达站点；
- 状态机：待开始 → 执行中 → 暂停/继续 → 完成/取消；
- 动作：开始、到达、确认取货、确认交付、完成、取消；
- 幂等：`request_id`，重复交付不重复记账；
- 模拟执行：沿折线推进，到站等待人工确认，刷新后可恢复；
- 真实模式：人工按清单执行，只有人工确认才记录交付。

### 4.5 道路异常与重规划

- 人工上报：选道路 → 文字说明 → 候选判断 → 人工确认 → 写入路况；
- 路况事件带**有效期**，过期自动失效；
- 重规划：保留已完成站点，只重排剩余站点；
- 不可达：明确提示，不伪造路线；
- 模拟经过两次可自动恢复临时路障；
- 实景演示：封路后路线绕行，计划版本递增。

### 4.6 实时语义接入（团队扩展）

- `POST /api/semantic-events`：接收上游视觉/语言系统的结构化结果；
- 消息字段：`event_id`、`task_id`、`obstacle_id`、`revision`、`map_version`、`edge_id`、`edge_fraction`、`category`、`passability`、`confidence`；
- 安全规则：
  - 先停车、再决策（停车独立事务先提交）；
  - 重复消息幂等；
  - 旧修订号不覆盖新状态；
  - 低置信度不能解除已确认障碍；
  - 解除需要复核证据；
  - 模拟任务与真实任务场景隔离；
- 决策动作：`observe`、`wait`、`replan`、`local_avoid`、`continue`；
- 局部绕行（纸箱等小障碍）只在原道路画短弧通过，不改全局路线；
- 施工/封路 → 重规划剩余站点；行人 → 先等待；
- 后台推进器约 0.1 秒推进模拟任务，不依赖浏览器；
- 命令行模拟上游：`python mock_upstream.py --demo`。

### 4.7 多 Agent 协作与痕迹

| Agent | 职责 | 记录的动作 |
| --- | --- | --- |
| 任务规划 Agent | 理解需求、补问、创建任务、生成计划 | `parse_task`、`create_task`、`plan_stops` |
| 道路观察 Agent | 图文异常候选判断 | `classify_hazard`（照片能力待接） |
| 调度复盘 Agent | 状态更新、重规划、接单、备注、报告 | `update_status`、`replan_task`、`accept_task`、`note_update` |

- 每次调用写入 `agent_traces`：输入摘要、输出摘要、工具、状态、耗时、时间；
- 执行面板显示最近 6 条，报告页显示完整时间线和调用统计；
- 痕迹中可直接看到“解析=`llm:deepseek-chat`”，作为真实模型调用的证据。

### 4.8 管理员视图

- 任务列表与筛选：全部 / 待接单 / 执行中 / 已完成；
- 接单：记录接单人与时间；
- 状态操作：开始、暂停、继续、取消、完成；
- 处理备注：写入任务时间线；
- 一键跳转工作台继续执行；
- 验收路径：非队员管理员可接单 → 处理 → 完成。

### 4.9 历史任务与报告

- 历史任务：状态、取货点、站点进度、截止、接单人、更新时间；
- 报告：完成率、已交付/总站点、计划版本、重规划次数、Agent 调用次数、站点明细、计划历史、道路事件、Agent 时间线；
- 支持浏览器打印 / 导出 PDF。

### 4.10 工程质量

- 单端口启动：FastAPI 同时托管页面、静态资源和 API；
- 一键启动：`start.bat`（Windows）/ `start.sh`；
- `.env` 自动加载，`.env` 与运行数据不提交；
- 20 条解析评测、ASGI 全链路测试、service 冒烟、语义桥/可见性/自动恢复测试；
- 前端 TypeScript 检查 + Babel 构建；
- Git 仓库与合并记录可复现。

## 5. 核心亮点

### 亮点 1：真实校园底图 + 80 个地点 + 任务级路网

- 不是抽象坐标，而是团队标注的真实校园示意图；
- 80 个地点全部接入道路网格，路线可达任意地点；
- 路线走横平竖直的道路，站点只用短入口线接入；
- 服务点密集时用“小蓝点 + 悬停名称”，兼顾信息量和可读性。

### 亮点 2：双解析通道 + 逐项补问 + 失败兜底

- 规则解析保证稳定，DeepSeek 提升泛化；
- 模型失败自动回落规则，不让主流程卡死；
- 缺信息不是“报错”，而是逐项问清楚；
- 20 条人工样例把“任务理解”变成可展示的分数。

### 亮点 3：多 Agent 协作“有痕迹”，不是三个名字

- 三个 Agent 有明确职责、工具和输入输出；
- 每次调用落库，页面和报告都能看到；
- Agent 只做理解与判断，路径、状态、指标由代码算；
- 答辩时可以直接展示调用时间线，证明协作过程。

### 亮点 4：异常处理是“任务级”，不是自动驾驶

- 小障碍：配送员自己绕/等，系统不改路线；
- 大障碍：封路后重排剩余站点，不可达明确提示；
- 上游语义接入：先停车、再决策、可观察/等待/局部绕行/重规划；
- 场景隔离：模拟障碍不污染真实任务。

### 亮点 5：管理员闭环与可追溯

- 接单、状态、备注全部落库；
- 备注写入任务时间线；
- 报告能回答“谁在什么时候做了什么”。

### 亮点 6：工程可复现

- 一条命令启动，前后端同源；
- 20 条评测 + 全量测试 + 冒烟流程；
- Git 提交与合并记录完整；
- 地图、解析、Agent、管理员都有验证证据。

## 6. 关键流程（答辩可讲）

### 6.1 任务创建

```text
用户输入：从教三楼取3份实验材料，送到科研楼、教四楼和学一公寓，教四楼优先，16:00前完成。
  ↓
规则/DeepSeek 解析：取货=教三楼；站点=3；教四楼优先；截止 16:00
  ↓
缺字段检查：齐全 → 允许创建
  ↓
写入任务、站点；记录“任务规划 Agent”痕迹
```

### 6.2 计划与执行

```text
生成计划：教四楼（优先）→ 学一公寓 → 科研楼；约 8 分钟
  ↓
开始 → 确认取货 → 模拟推进/人工到达
  ↓
逐站确认交付 → 完成
  ↓
报告：完成率、计划版本、Agent 调用次数
```

### 6.3 异常与重规划

```text
用户在地图选一条路 → 上报“施工封闭”/上传照片
  ↓
道路观察 Agent 给候选 → 人工确认
  ↓
写入路况（可设有效期）
  ↓
调度复盘 Agent 重规划：保留已完成站点，只排剩余
  ↓
不可达站点明确提示；计划版本 +1
```

### 6.4 上游语义接入

```text
上游消息（结构化）→ 校验 → 先停车
  ↓
道路观察 Agent 整理判断 → 调度复盘 Agent 决策
  ↓
observe / wait / local_avoid / replan / continue
  ↓
路线可行且允许恢复 → 自动放行；否则保持停车
```

## 11. 三分钟演示脚本

1. **打开工作台**：输入“从教三楼取3份材料送到科研楼、教四楼和学一公寓，教四楼优先，16:00前完成”，点解析；
2. **展示补问**：故意删掉物品，展示“第 N 站缺少物品”卡片，补全后再创建；
3. **生成计划**：展示优先站点前置、地图路线、ETA；
4. **执行**：开始 → 确认取货 → 模拟到达 → 确认交付；
5. **异常**：地图选中一条路，上报“施工封闭”，展示 Agent 痕迹和重规划；强调“已完成站点保留”；
6. **管理员**：切到管理员视图，接单、写备注；
7. **报告**：展示完成率、计划版本、Agent 调用；
8. **收尾**：明确“不做自动驾驶、模拟与真实隔离、路况为人工/上游上报”。

## 12. 答辩常见问题

**Q1：这和自动驾驶/智能车有什么区别？**  
A：我们不控制车辆，也不做局部实时避障。系统解决的是任务级问题：哪条路封了、剩余站点怎么排、哪些站点不可达。局部绕行只存在于模拟演示。

**Q2：多 Agent 是不是只是分了几个函数？**  
A：三个 Agent 有明确职责、工具和输入输出，每次调用写入 `agent_traces`，页面和报告可查；推理归 Agent，路径、状态、指标由代码计算。不是三个名字，也不是三个聊天窗口。

**Q3：为什么不用 LangChain / ReAct / 微调？**  
A：业务确定性高、流程短，直接函数编排更透明、可复现；20 条样例是测试集不是训练集；微调成本和风险高。我们把精力放在真实模型调用、失败兜底、可核查痕迹和测试上。

**Q4：地图数据哪来的？**  
A：团队标注的校园示意图 + 队友 `map_design` 结构化数据；地点和路网是示意，未实地测绘，页面有明确声明。

**Q5：模型失败/断网怎么办？**  
A：自动回落规则解析并标注；`/api/health` 可看模型是否配置；接口测试默认禁用外部模型，避免依赖网络。

**Q6：封路要天天更新吗？**  
A：不需要。事件驱动 + 有效期，到期自动失效；管理员可续期/解除；没有上报时默认通行。

**Q7：照片视觉分析还没做，怎么解释？**  
A：这是唯一剩余功能缺口；文字异常与上游语义已完整跑通。下一步接上传 + 视觉候选 + 人工确认，不训练模型，用现成多模态接口。

## 13. 一句话收尾

> CampusPilot 把“校园配送”从口头和纸单，变成**可解析、可规划、可执行、可重规划、可追溯**的任务系统；它不替人开车，但替人把复杂情况想清楚。
