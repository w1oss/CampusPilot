第 1 页 · 封面

标题：CampusPilot

副标题：校园低速配送任务 Agent

底部信息：团队 / 日期 / github.com/w1oss/CampusPilot

页面要点

  • 一句话定位：把一句配送需求变成可执行、可追溯的任务
  • 关键词：任务规划 · 异常重规划 · 多 Agent 协作 · 管理员闭环
  • 明确边界：不是自动驾驶，不控制真实车辆

配图建议：校园地图全景（docs/campus-map-preview.svg）作为半透明背景 + 工作台截图。

讲稿提示：“我们做的不是一辆车，而是一个调度员。”

第 2 页 · 场景背景

标题：校园配送，难在“变化”

一句话：不是送不到，是封路、改时间、加站点之后不知道怎么改。

页面要点

  • 多站点、时间窗、优先级靠经验，顺序容易冲突
  • 施工、活动封路后，原路线失效，剩余站点要重排
  • 需求在微信、路线在纸上、异常靠电话，信息分散
  • 模拟数据和真实配送混在一起，验收与追责困难

配图建议：四象限痛点图；左侧“现状”，右侧“后果”。

讲稿提示：把痛点落在“变化”和“不可追溯”两个词上。

第 3 页 · 方案总览

标题：不替人开车，替人想清楚怎么送

一句话：自然语言 → 结构化任务 → 计划 → 执行 → 异常 → 报告。

页面要点

  • 发起人：一句话描述需求，缺什么系统逐项问
  • 配送员：按清单执行，异常时上报或接收上游消息
  • 管理员：接单、改状态、写备注、看报告
  • 闭环：解析 → 补问 → 计划 → 执行 → 重规划 → 报告

配图建议：横向闭环流程图（6 个节点），底部标注三类用户。

讲稿提示：强调“任务级”，不是“车辆控制级”。

第 4 页 · 功能架构

标题：Agent 判断，代码计算

一句话：模型只做理解和判断，路径、状态、指标由确定性代码算。

页面要点

  • 交互层：工作台 / 校园地图 / 执行控制 / 管理员 / 报告
  • Agent 层：任务规划 / 道路观察 / 调度复盘
  • 确定性引擎：白名单校验、Dijkstra、站点排序、状态机、模拟器、报告
  • 数据层：SQLite + 地图 JSON + 校园底图
  • 约束：Agent 不能直接确认交付、不能直接改路况

配图建议：五层架构图；右侧用红色标注“Agent 不越权”。

讲稿提示：这是后面所有亮点的地基。

第 5 页 · 任务理解

标题：一句话变成可执行任务

一句话：规则保证稳定，DeepSeek 提升泛化，缺信息逐项问。

页面要点

  • 规则 + DeepSeek 双通道，模型失败自动回落并标注
  • 地点白名单校验，模型不能编造新地点
  • 缺取货点 / 站点 / 物品：页面逐项补问，补全前不能创建
  • 白名单外地名明确提示，不静默丢弃
  • 20 条人工样例：规则 20/20，DeepSeek 20/20（18 模型 + 2 兜底）

配图建议：解析界面 + 补问卡片 + 评测输出截图（三张小图并排）。

讲稿提示：重点讲“失败兜底”和“追问”，不要只讲模型。

第 6 页 · 地图与路网

标题：真实校园底图，80 个地点可达

一句话：不是抽象坐标，是团队标注的北邮西土城路校区。

页面要点

  • 底图 2491×3509，团队标注示意图
  • 80 个可交互地点：41 栋建筑 + 39 个服务点；另有 6 个校门
  • 路网 217 节点 / 261 段，6 纵 × 10 横
  • 路线只走道路网格，站点用短入口线接入
  • 服务点小蓝点 + 悬停名称，避免标签重叠

配图建议：地图全图 + 局部放大（教三楼、图书馆、宿舍区）。

讲稿提示：强调“真实布局 + 可计算”，不是一张图片。

第 7 页 · 计划与执行

标题：优先站点先送，状态全程可追溯

一句话：排序、路线、状态机、模拟/真实隔离。

页面要点

  • 排序：优先站点前置 + 截止时间约束
  • 路线：Dijkstra，支持单行道与封路
  • 状态机：待开始 → 执行中 → 暂停/继续 → 完成/取消
  • 动作幂等：request_id，重复交付不重复记账
  • 模拟与真实隔离：模拟结果不计入真实成果

配图建议：执行面板（计划摘要 + 站点清单 + 状态按钮）。

讲稿提示：强调“刷新可恢复”和“人工确认才记账”。

第 8 页 · 异常与重规划

标题：封路后，保留已完成，只重排剩余

一句话：异常不是报错，是重新算一遍剩下的任务。

页面要点

  • 地图选路 → 文字/照片 → 候选判断 → 人工确认
  • 路况事件带有效期，到期自动失效
  • 重规划保留已完成站点，只排剩余
  • 不可达站点明确提示，不伪造路线
  • 计划版本递增，操作可追溯

配图建议：封路前后路线对比（两张地图）+ 重规划结果。

讲稿提示：这是“任务级决策”最直观的一页。

第 9 页 · 实时语义接入

标题：接收上游感知，先停车再决策

一句话：摄像头/视觉模型看，CampusPilot 决定怎么改任务。

页面要点

  • 结构化消息：道路、位置、类别、通行性、置信度
  • 先停车（独立事务）→ 道路观察 → 调度决策 → 放行
  • 决策：观察 / 等待 / 局部绕行 / 重规划 / 继续
  • 安全规则：幂等、修订号、低置信度不解除、复核证据
  • 场景隔离：模拟障碍不污染真实任务

配图建议：语义事件面板 + 停车/放行状态截图。

讲稿提示：这是团队扩展模块，不夸大“自动驾驶”，强调任务级。

第 10 页 · 多 Agent 协作

标题：三个角色，有痕迹才叫协作

一句话：不是三个名字，是三次可核查的调用。

页面要点

  • 任务规划 Agent：解析、补问、创建任务、生成计划
  • 道路观察 Agent：异常候选判断
  • 调度复盘 Agent：状态、重规划、接单、备注、报告
  • 每次调用落库：输入摘要、输出摘要、工具、耗时
  • 页面时间线 + 报告调用统计；痕迹显示 解析=llm:deepseek-chat

配图建议：执行面板“Agent 协作记录”时间线 + 报告统计截图。

讲稿提示：直接展示痕迹，不讲概念。

第 11 页 · 管理员与报告

标题：谁接的单、改了什么，都能查

一句话：接单、状态、备注、报告形成管理闭环。

页面要点

  • 任务筛选：全部 / 待接单 / 执行中 / 已完成
  • 接单：记录接单人与时间
  • 状态操作：开始、暂停、继续、取消、完成
  • 处理备注：写入任务时间线
  • 报告：完成率、计划版本、重规划次数、Agent 调用次数
  • 验收路径：非队员可独立完成一次任务

配图建议：管理员视图 + 报告页。

讲稿提示：强调“非队员可操作”，这是验收点。

第 12 页 · 码道应用

标题：用码道把“想法”变成可运行系统

一句话：从需求解析到代码、测试、合并、文档，全流程有迹可循。

页面要点

  • 需求解析：两份方案 docx → 验收标准与技术约束
  • 代码审查：发现前端构建链路冲突、地图字段遗漏
  • 开发：前后端功能、80 地点路网、Agent 痕迹、管理员视图
  • 测试：20 条评测、ASGI 全链路、合并回归
  • 合并：拉取队友 zzz 分支，解决 db.py/service.py 冲突
  • 原则：AI 产出必须编译、测试、人工确认；不虚构效率百分比

配图建议：码道对话截图 + 测试输出 + Git 合并记录。

讲稿提示：这页要真实截图，不讲空话。

第 13 页 · 验证与边界

标题：能跑、能复现、边界清楚

一句话：诚实的边界比夸大的能力更加分。

页面要点

  • 80 个地点两两可达；规则与 DeepSeek 均 20/20
  • 前端 TypeScript/构建通过；后端全量测试通过
  • 单端口启动：start.bat → http://127.0.0.1:8000/
  • 边界：不做自动驾驶；局部绕行仅模拟；路况来自人工/上游
  • 后续：照片上传 + 视觉异常分析；真实用户试用

配图建议：测试输出 + 路线图（已完成 / 下一步）。

讲稿提示：主动讲边界，避免评委追问。

附 C：制作提示

  1. 一页一个观点：不要在一页塞满功能清单；
  2. 数字放大：80 个地点、217 节点、261 段、20/20；
  3. 先图后字：地图、时间线、路线对比优先于文字；
  4. 边界单独讲：第 13 页主动说明“不做自动驾驶”；
  5. 未完成不冒充：照片视觉分析放在“后续规划”；
  6. 码道页要真实：用真实对话/测试/提交截图，不编造效率数字。

附 D：3 分钟演示顺序（与 PPT 对应）

  1. 打开工作台，输入需求（第 5 页）
  2. 展示补问卡片（第 5 页）
  3. 生成计划，看地图路线（第 6、7 页）
  4. 开始/取货/交付（第 7 页）
  5. 上报封路，展示重规划（第 8 页）
  6. 切到管理员视图，接单/备注（第 11 页）
  7. 打开报告，看 Agent 调用（第 10、11 页）
  8. 收尾讲边界与后续（第 13 页）
